# Почему парсер — отдельный микросервис, а не часть PCMEF backend

## Причины

1. **Разные технологические стеки.** Парсинг сайта университета (cookie-авторизация, в перспективе — обход капчи) реализован на Python (FastAPI, BeautifulSoup, httpx) — экосистема, удобная для веб-скрейпинга. Backend — Kotlin/Spring. Сведение в один процесс потребовало бы либо переписать парсер на Kotlin, либо звать Python через FFI/subprocess — оба варианта дороже по времени, чем HTTP-интеграция.
2. **Разные жизненные циклы.** Парсер может падать/перезапускаться/долго работать (синхронизация расписания — фоновая задача) независимо от доступности backend для пользователей.
3. **Разделение данных.** Парсер хранит сырые данные ИС вуза (институты, специальности, группы, преподаватели, аудитории, занятия) в своей БД `uniplanner_parser`. Backend хранит только пользовательские данные и кэш расписания (`uniplanner_backend`) — нет совместного владения схемой.

## Как это согласуется с PCMEF

Методичка допускает отступление от «1:1» применения PCMEF при наличии микросервисной архитектуры (см. вводные проекта). Решение:

- PCMEF применяется целиком к **backend-монолиту** (см. `pcmef-mapping.md`).
- Парсер для backend — внешняя зависимость, вызываемая из слоя **Foundation** (`ParserClient`, планируется) точно так же, как вызов внешнего REST API или БД — то есть микросервис логически "ниже" Foundation, а не отдельный слой PCMEF.
- Контракт между сервисами зафиксирован в `api/parser-api.yaml`.

## Текущий статус

В этой итерации интеграция реализована в **mock-режиме**: backend читает расписание только из собственного кэша (`cached_lessons`), заполненного seed-миграцией, без живого вызова парсера. Причина — экономия времени перед дедлайном (см. `docs/08-final/summary.md`). Архитектурная граница (backend ↔ parser через HTTP, разные БД) спроектирована заранее именно для того, чтобы включение живой интеграции не требовало изменения архитектуры — только реализации `ParserClient` и эндпоинтов чтения в parser.
