# ADR-001: Выбор траектории и архитектурного стиля

**Статус:** Принято
**Контекст:** курсовой проект по дисциплине «Программная инженерия»

## Контекст

Нужно выбрать траекторию курсового проекта и соответствующий архитектурный стиль, учитывая объём времени одного разработчика и наличие готового стороннего источника данных расписания (сайт вуза).

## Рассмотренные варианты

### Вариант 1: Траектория А (Desktop-монолит)
Один процесс, без REST API и веб-клиента.

**Минусы:** не позволяет использовать React-фронтенд и REST API, которые уже планировались под учебные цели; ниже потолок оценки.

### Вариант 2: Траектория Б — Web-ориентированная (выбрана) ✅
Тонкий веб-клиент (React) + сервер (Spring Boot) + REST API + PostgreSQL. PCMEF применяется к backend-монолиту.

**Плюсы:**
- Соответствует объёму одного разработчика в отведённый срок.
- REST API + JWT + ролевая модель — соответствует обязательным требованиям трактории.
- Открывает дорогу архитектурному запасу (KMP shared-модуль) без переписывания контракта данных.

**Минусы:** не требует Desktop/Enterprise-уровня (CI/CD, второй полноценный клиент) — сознательно, так как это превышает объём текущей итерации.

### Вариант 3: Траектория Г (Enterprise: Desktop + Web + CI/CD)
**Минусы:** требует второй полноценный UI-клиент (Desktop) и CI/CD-пайплайн — нереалистично для срока и состава команды (один разработчик).

## Решение

Траектория Б. Микросервис-парсер не считается вторым клиентом — это вспомогательный источник данных, вызываемый backend'ом (см. [adr-002](adr-002-parser-microservice.md)).

## Последствия

- Архитектурный потолок ниже, чем у Enterprise-траектории, но реалистично достижим в одиночку.
- KMP shared-модуль и Android-задел зафиксированы как бонус, не обязательное требование (см. [00-project-charter/passport.md](../../00-project-charter/passport.md)).
