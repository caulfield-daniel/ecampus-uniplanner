# ADR-002: Парсер расписания — отдельный микросервис

**Статус:** Принято

## Контекст

Нужно получать расписание занятий с сайта вуза (ecampus.ncfu.ru), включая обход капчи для личного входа пользователя. Backend написан на Kotlin/Spring.

## Рассмотренные варианты

### Вариант 1: Парсинг внутри backend (Kotlin)
**Минусы:** экосистема веб-скрейпинга (BeautifulSoup-аналоги, обход капчи) на JVM значительно слабее, чем в Python; смешивание ответственностей в одном процессе.

### Вариант 2: Отдельный микросервис на Python (FastAPI) ✅ Выбран
Парсер — самостоятельный процесс (FastAPI, BeautifulSoup, httpx, SQLAlchemy), со своей БД `uniplanner_parser`. Backend обращается к нему через HTTP (`ParserClient`, Foundation-слой).

**Плюсы:**
- Подходящая экосистема для скрейпинга и обхода капчи на стороне парсера.
- Независимые жизненные циклы — падение/перезапуск парсера не блокирует backend для пользователей.
- Разделение данных: парсер хранит сырые справочники вуза, backend — только пользовательские данные и кэш расписания.

**Минусы:** два процесса для локального запуска вместо одного — компенсируется Docker Compose.

### Вариант 3: Полная интеграция через общую БД
**Минусы:** совместное владение схемой между разными технологическими стеками — нарушает границы ответственности, усложняет миграции.

## Решение

Парсер — отдельный микросервис. Для backend он внешняя зависимость уровня Foundation (`ParserClient`, `WebClient`), а не отдельный слой PCMEF — методичка допускает такое отступление при микросервисной архитектуре.

## Последствия

- Контракт между сервисами зафиксирован в `api/parser-api.yaml`.
- Синхронизация (`POST /parser/sync`) — ручная, без cron (см. [01-requirements/use-case-specifications.md](../../01-requirements/use-case-specifications.md), UC-07).
