# ADR-003: Общая модель данных через Kotlin Multiplatform shared-модуль

**Статус:** Принято

## Контекст

DTO для REST API (запросы/ответы, правила валидации) нужно поддерживать синхронно между backend (Kotlin/JVM) и фронтендом (TypeScript). Дублирование моделей вручную — источник рассинхрона.

## Рассмотренные варианты

### Вариант 1: Дублировать DTO вручную (Kotlin data class + TS interface)
**Минусы:** изменение поля требует правок в двух местах; легко забыть синхронизировать.

### Вариант 2: Генерация TS-типов из OpenAPI-спецификации
**Минусы:** требует поддерживать `api/*.yaml` синхронно с кодом контроллеров отдельно; добавляет шаг генерации.

### Вариант 3: Kotlin Multiplatform shared-модуль (JVM + JS таргеты) ✅ Выбран
Один Kotlin-модуль (`shared/`) с `@Serializable @JsExport` data-классами и общими правилами валидации (`ModelValidators`), компилируется и в JVM (используется backend'ом напрямую), и в JS (бандл, типы реэкспортируются во фронтенд).

**Плюсы:**
- Один источник истины для DTO и правил валидации — работает одинаково на backend и потенциальном мобильном клиенте.
- Архитектурный задел под Android-клиент без переписывания моделей.

**Минусы:**
- Генерация `.d.mts` из Kotlin/JS оказалась нестабильной на машине разработки — потребовался обходной путь (локальная TS-аугментация типов), см. [05-implementation/code-structure.md](../../05-implementation/code-structure.md).
- Классы, экспортированные в JS, генерируют методы (`copy`/`equals`/`hashCode`), не проходящие структурную проверку TS для литералов объектов — тела запросов объявлены как локальные `*Dto`-интерфейсы во фронтенде, а не импортируются из shared.

## Решение

KMP shared-модуль остаётся источником истины для DTO; известные шероховатости толчейна задокументированы и обходятся локально, не блокируя разработку.
