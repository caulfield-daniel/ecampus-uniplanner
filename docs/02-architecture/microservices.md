# Почему парсер — отдельный микросервис, а не часть PCMEF backend

## Причины

1. **Разные технологические стеки.** Парсинг сайта университета реализован на Python (FastAPI, BeautifulSoup, httpx) — экосистема, удобная для веб-скрейпинга. Backend — Kotlin/Spring. Сведение в один процесс потребовало бы либо переписать парсер на Kotlin, либо звать Python через FFI/subprocess — оба варианта дороже по времени, чем HTTP-интеграция.
2. **Разные жизненные циклы.** Парсер может падать/перезапускаться/долго работать (синхронизация расписания — фоновая задача) независимо от доступности backend для пользователей.
3. **Разделение данных.** Парсер хранит сырые данные ИС вуза (институты, специальности, группы, преподаватели, аудитории, занятия) в своей БД `uniplanner_parser`. Backend хранит только пользовательские данные и кэш расписания (`uniplanner_backend`) — нет совместного владения схемой.

## Как это согласуется с PCMEF

Методичка допускает отступление от «1:1» применения PCMEF при наличии микросервисной архитектуры (см. вводные проекта). Решение:

- PCMEF применяется целиком к **backend-монолиту** (см. [pcmef-diagram.md](pcmef-diagram.md)).
- Парсер для backend — внешняя зависимость, вызываемая из слоя **Foundation** (`ParserClient`) точно так же, как вызов внешнего REST API или БД — то есть микросервис логически "ниже" Foundation, а не отдельный слой PCMEF.
- Контракт между сервисами зафиксирован в `api/parser-api.yaml`.

## Текущий статус

Живая интеграция реализована: `ParserSyncController` (`POST /parser/sync`) вызывает `ParserClient` (Foundation, `WebClient`), который обращается к уже накопленным parser'ом данным реального вуза и сохраняет/обновляет их в `cached_lessons` backend'а. Массово проверено: синхронизированы все 866 групп, известных парсеру — реальные данные вуза за весенний семестр 2026 (март — середина июня, дальше идёт летняя сессия/каникулы, новый семестр на сайте пока не опубликован).

Синхронизация backend ← parser — ручная, без cron (вызывается по необходимости, см. UC-07 в [01-requirements/use-case-specifications.md](../01-requirements/use-case-specifications.md); инструкция по ручному запуску — [08-deployment/admin-guide.md](../08-deployment/admin-guide.md)). Demo-данные из `V2__seed_demo_lessons.sql` используют названия реальных групп (`ИВТ-21-1`/`ИВТ-22-2`) — после массовой синхронизации для этих двух групп в кэше совместно лежат и demo-строки, и реальные занятия; это не конфликт (разные даты в одной таблице), но и не идеальная гигиена данных.

**Парсер запускается на хосте, backend — в Docker:** `localhost` внутри контейнера backend'а указывает на сам контейнер, а не на хост, поэтому `PARSER_BASE_URL` в `docker-compose.yml` явно указывает на `host.docker.internal` (с `extra_hosts: host-gateway` для Linux-докера).

## Важный архитектурный инсайт: расписание парсится без авторизации

Эмпирически подтверждено (2026-06-24): эндпоинт расписания вуза (`POST /schedule/GetSchedule`) отдаёт полные данные **без какой-либо авторизации** — запрос без cookies возвращает реальные занятия. Сервисный аккаунт парсера (`parser/cookies.json` + `CookieFileAuthenticator`) был нужен по умолчанию для всех сценариев, но это избыточно для самого расписания.

Сделано: добавлен `NoAuthAuthenticator` (`parser/app/services/auth/no_auth.py`, `ensure_session()` всегда возвращает `true`), и инкрементальный sync расписания (`ParserRunner.run_incremental_parse`, `POST /parser/run-incremental`) переключён на него. Полный парсинг (`run_full_parse` — институты/специальности/группы) пока оставлен на `CookieFileAuthenticator`, так как не проверялось, нужна ли там авторизация.

**Практическое следствие:** обычный re-scrape расписания больше не блокируется протухшей cookie-сессией сервисного аккаунта — она нужна теперь только для `run_full_parse` (открытие новых институтов/специальностей/групп) и для совершенно отдельного личного флоу пользователя (`/university-auth/*`, капча, привязка собственного аккаунта — нужна для будущих оценок/статистики студента, не для расписания).

**Архитектурное направление на будущее (зафиксировано пользователем, не реализовано в этой итерации):** поскольку расписанию авторизация не нужна, сервисный аккаунт для него в принципе избыточен — парсинг расписания может стать полностью автоматическим/полуавтоматическим (например, по cron), без риска протухания сессии. Личный вход через ecampus.ncfu.ru имеет смысл сохранить только там, где он действительно нужен: для автоматического определения группы студента и (в будущем) получения его персональной статистики/оценок — не для самого расписания.
