## Что сделано с прошлой ревизии

- **Реальные данные расписания загружены для всех 866 групп**, известных парсеру (весенний семестр 2026, март — середина июня). Инструкция по ручной синхронизации (до появления админ-панели) — `docs/08-deployment/admin-guide.md`, утилита `parser/bulk_sync.py`.
- **Архитектурный инсайт пользователя подтверждён и применён**: эндпоинт расписания вуза (`/schedule/GetSchedule`) не требует авторизации. Добавлен `NoAuthAuthenticator` (`parser/app/services/auth/no_auth.py`), `ParserRunner.run_incremental_parse` переключён на него — обычный re-scrape расписания больше не блокируется протухшей cookie-сессией сервисного аккаунта. `run_full_parse` (институты/специальности/группы) пока не трогали — не проверялось, нужна ли там авторизация.
- **Исправлен реальный баг**: `ParserSyncServiceImpl.syncGroupSchedule` падал на повторном sync уже существующих данных (`No EntityManager with actual transaction available` — derived delete-запрос Spring Data без `@Transactional`). Маскировался при первой синхронизации (нечего удалять). Подтверждено полным прогоном 866/866 групп без ошибок.
- **Исправлен баг сети Docker**: backend в контейнере не мог достучаться до парсера на хосте через `localhost` — добавлен `PARSER_BASE_URL=http://host.docker.internal:8000` + `extra_hosts` в `docker-compose.yml`.
- **Плейсхолдеры заголовков исправлены**: `web/index.html` (`<title>uniplanner web</title>` → `UniPlanner`), `web/package.json` (`"name": "web-tmp"` → `"uniplanner-web"`).

## Будущая архитектурная задача (зафиксирована в памяти, не реализована)

Поскольку расписанию авторизация не нужна, сервисный аккаунт парсера в перспективе избыточен для самого расписания — парсинг может стать автоматическим/полуавтоматическим (cron). Личный вход через ecampus.ncfu.ru имеет смысл сохранить только для того, что реально требует авторизации: автоопределение группы студента и (в будущем) его персональная статистика/оценки. Объединение входа в приложение с капча-логином ИС вуза прямо на экране логина — отдельная отложенная задача (см. таск #17 в TaskList и память `project-future-login-time-uniauth`).

## Известные нерешённые вопросы

### 1. Генерация `.d.mts` из Kotlin/JS — всё ещё нестабильна
Не тронуто в этой ревизии. Воркэраунд (`relatedLessonId` через intersection-type в `web/src/shared/types/index.ts`) остаётся. На отдельной заброшенной ветке `kmp-shared-rework` (HEAD `740cf79`) есть незавершённый эксперимент с `generateTypeScriptDefinitions()` — встроенным механизмом KMP, потенциально настоящий фикс. См. `git diff dev kmp-shared-rework -- shared/build.gradle.kts`. Не пытаться merge/rebase саму ветку — она ветвилась от кода до FSD-рефактора.

### 2. Личный вход в ИС вуза — нет экрана во фронтенде
`UniversityAuthController`/`/university-auth/*` полностью реализован на backend (капча, шифрование сессии), но не вызывается ни из одной страницы `web/src/pages/`. См. «Будущая архитектурная задача» выше — это теперь его единственное реальное назначение (группа + оценки/статистика), не расписание.

### 3. Отложено явно пользователем
Админ-панель для управления синхронизацией расписания — **не начата, обсуждение отложено**. Не начинать без явного запроса.

### 4. `run_full_parse` не проверялся на работу без авторизации
Только `run_incremental_parse` (схему расписания) переключили на `NoAuthAuthenticator`. Если понадобится открывать новые институты/специальности/группы — стоит сначала проверить, не нужна ли там авторизация так же, как не нужна для расписания, прежде чем тратить время на обновление cookies.
